# 온톨로지 적용 가능성 검토 (Prometheus 중심)

이 문서는 계획이 아니라 판단이다. "공공 API 문서에 온톨로지를 도입할 수 있는가"를
현재 구현 기준으로 따져 적용 지점, 비용, 착수 조건을 정한다. 구현을 승인하는 문서가
아니며, 5절의 계측 게이트를 통과하기 전에는 어떤 코드도 추가하지 않는다.

## 0. 결론

- RDF·OWL·SPARQL·트리플스토어·추론기는 **도입하지 않는다.** 현재 필요한 추론은
  "두 필드가 같은 것을 가리키는가", "같은 코드체계인가", "상위 분류가 같은가" 셋뿐이고
  이는 사전 조회로 끝난다. 추론 엔진을 들이면 표준 라이브러리 원칙과 결정형 검증 원칙이
  동시에 깨진다.
- 성립하는 형태는 하나다. **결정형 개념 사전 한 겹**(JSONL, 근거 필드 포함)을
  `services/search`가 소유하고, Prometheus는 그것을 HTTP 상세 응답으로만 읽는다.
  온톨로지는 산출물이 아니라 이름 정규화 자원이다.
- 효과가 가장 큰 지점은 검색이 아니라 **A3 바인더의 `step_field` 연결**이다.
  거기서 이름이 어긋나면 문서 간 체인이 끊기고 시나리오가 문서 열람형으로 수렴한다.
- 착수 조건은 5절의 계측이다. 강등률이 낮으면 이 검토는 "적용 가능하지만 이득이 없음"으로
  종결한다.

| 영역 | 적용 가능성 | 근거 |
|---|---|---|
| A3 바인더 `step_field` 연결 | 높음 | 지금은 이름 불일치 = 즉시 입력 승격. 체인이 사라진다 |
| A4 검증(코드체계 충돌) | 높음 | 이름만 같고 체계가 다른 연결을 지금은 아무도 막지 않는다 |
| search 관계 추출(io-chain) | 높음 | 판정이 소문자 완전일치 하나뿐이다 |
| search 관계 추출(same-domain) | 즉시 | 온톨로지 없이 분류체계 2단계 분해만으로 개선된다 |
| 검색 랭킹 | 낮음 | 벡터 채널이 유사어를 이미 일부 흡수한다 |
| B단계 N3 파라미터 4분류 | 낮음 | 이미 닫힌 소문자 목록이고 문제가 보고된 적 없다 |
| combiner 조합 제안 | 낮음 | 출력이 자유 텍스트라 정규화 이득이 남지 않는다 |

## 1. 이미 온톨로지 없이 온톨로지 일을 하고 있다

새로 들이자는 이야기가 아니라, 흩어져 있는 손코딩을 한 겹으로 모을 수 있는지가 질문이다.

- `services/search/backend/relations/extractor.py` — `io-chain`과 `param-overlap`은
  요청·응답 필드 이름을 소문자로 낮춘 뒤 **집합 교집합**으로 판정한다. 동의어, 약어,
  스네이크/카멜 표기 차이는 전부 비일치다.
- 같은 파일의 `same-domain`은 분류체계를 **문자열 전체 일치**로 본다. 반면
  `services/combiner/app/prompts.py:45`는 같은 값을 `" - "`로 잘라 상위 분야만 쓴다.
  같은 소스 문자열을 두 서비스가 다른 입도로 읽고 있다.
- `services/search/backend/search/coverage.py` — 광역시도 정식/축약 명칭 하드코딩 목록.
  행정구역 계층의 손코딩 대체물이며, 모듈 주석 스스로 "카탈로그에 커버리지 필드가 없으므로
  없는 값을 추론해 만들지 않는다"고 적어 두었다.
- `services/search/backend/catalog/document_builder.py` — 상세 응답 계약에 이미
  `concept_id`, `term_canonical_ko`, `aliases`, `confidence`, `review_status`,
  `match_source`가 있다. 소스는 `03_semantic/{concepts,field_mappings,service_tags}.jsonl`인데
  **현재 크롤러는 이 산출물을 만들지 않는다.** 즉 스키마는 있고 데이터가 없다.

마지막 항목이 이 검토의 실질적 배경이다. 착지점이 이미 정의돼 있어 도입 비용의 절반은
지불된 상태지만, 동시에 CLAUDE.md의 "현재 구현과 테스트에 필요한 코드만 유지한다"에
어긋나는 비활성 경로다. 채우거나 지우거나 둘 중 하나여야 하며, 이 검토는 그 결정을
계측에 걸어 두는 것이다.

## 2. Prometheus에서 값이 나오는 지점

### 2.1 A3 바인더 (가장 큼)

`scenario-factory-plan.md` 6절 표에 이렇게 적혀 있다.

> `step_field`가 앞 단계 `output_fields`에 없음 → 그 필드를 앞 단계 출력에 추가,
> 응답 필드에도 없으면 `input`으로 승격

문서 A의 응답이 `stationName`이고 문서 B의 요청이 `stnNm`이면 개념은 같지만 이름이 다르다.
바인더는 이를 사용자 입력으로 승격시킨다. 결과적으로 두 문서는 한 화면에 있을 뿐 **연결되지
않고**, 시나리오는 7절 폴백과 구분이 어려운 문서 열람형으로 수렴한다. 공장의 산출물이
"여러 문서를 엮은 이용 흐름"이라는 목표에 정확히 반대되는 실패다.

개념 동치가 있으면 승격 대신 연결이 남는다. 이것이 온톨로지가 Prometheus에서 값을 만드는
1순위 지점이다.

### 2.2 A4 검증 (안전성)

이름 일치는 의미 일치가 아니다. 다음은 이름이 같거나 비슷해서 이어지지만 실제로는
빈 응답이나 오답을 내는 조합이며, 현재 어떤 검사도 이를 막지 않는다.

| 충돌 | 예 |
|---|---|
| 코드체계 | 법정동코드 ↔ 행정동코드, 사업자번호 ↔ 법인번호 |
| 좌표계 | WGS84 경위도 ↔ TM/UTM-K 좌표 |
| 시간 형식 | `yyyyMMdd` ↔ `yyyy-MM-dd` ↔ `yyyyMMddHHmm` |
| 단위 | ㎍/㎥ ↔ ppm, ㎡ ↔ 평 |

개념에 `code_system`·`unit`을 두면 A4에 결정형 검사 하나를 추가할 수 있다. LLM run을 늘리지
않고, 사전 조회만으로 판정되며, 위반 시 근거 문자열을 findings에 남길 수 있다. critic의
기존 성격(로컬 결정형 검증)과 정확히 같은 종류의 검사다.

여기서 온톨로지는 기능이 아니라 **안전 장치**다. 이름만 보고 이어붙인 체인은 조용히 실패해
사용자가 "빈 표"를 받는데, 그 실패는 지금 어디에도 기록되지 않는다.

### 2.3 값이 크지 않은 지점

- **검색 랭킹**: 벡터 채널이 유사어를 일부 흡수하고 있고, RRF 융합 위에 신호를 하나 더
  얹는 일은 `COVERAGE_PRIOR_BONUS` 주석이 보여 주듯 튜닝 비용이 크다. 개념 사전을
  `_build_search_blob`의 `semantic` 슬롯에 넣는 것은 가능하지만 우선순위가 아니다.
- **B단계 N3**: auth/paging/format 4분류는 이미 닫힌 목록이고 실패 사례가 없다. 개념
  사전으로 흡수할 수는 있으나 지금 옮기면 이득 없이 결합만 늘어난다.

## 3. 비용과 위험

1. **온톨로지는 코드가 아니라 데이터 자산이다.** 유지 주체가 없으면 원문 문서가 바뀌는
   순간부터 조용히 어긋난다. 그래서 매핑마다 `match_source`·`confidence`·`review_status`가
   필수이며, 근거 없는 매핑은 관계·바인딩에 쓰지 않는다. 문서 최신성 검사(`freshness.py`)와
   같은 계열의 규율이 사전에도 필요하다.
2. **LLM으로 사전을 만들면 원칙이 깨진다.** CLAUDE.md는 LLM 출력에서 service_id만 읽고
   나머지는 Nara 원본에서 다시 조회하도록 못박고 있다. 사전 생성은 오프라인 배치의
   결정형 규칙(표기 정규화, 접미사 사전, 빈도 집계)과 사람 검토로만 한다. 런타임에
   개념을 만들어 내지 않는다.
3. **표준 어휘 수입은 하지 않는다.** 외부 온톨로지를 들여오면 우리 문서에 근거가 없는
   개념이 사전에 섞이고, "문서에 실재하지 않는 참조는 제거한다"는 A단계 계약과 충돌한다.
   사전은 우리 문서에 실제로 등장한 필드명에서만 자란다.
4. **범위 확산.** 개념 사전이 생기면 곧바로 "개념으로 검색", "개념 그래프 시각화",
   "개념 기반 자동 조합" 요구가 따라온다. 이 검토는 그 어느 것도 승인하지 않는다.

## 4. 성립한다면 이 계약이다

`03_semantic` 스키마를 새로 만들지 않고, `document_builder`가 이미 읽고 있는 키를 그대로
채운다. 새 필드는 개념 쪽의 `kind`·`code_system`·`unit`·`broader` 넷뿐이다.

```jsonc
// concepts.jsonl
{"concept_id": "c.station_name",
 "canonical_ko": "측정소명",
 "aliases": ["stationName", "stnNm", "측정소_명"],
 "kind": "name",              // identifier | code | measure | time | location | name
 "code_system": "",           // kind=code일 때만 채운다 (예: "법정동코드")
 "unit": "",                  // kind=measure일 때만 채운다
 "broader": "c.station"}

// field_mappings.jsonl  (기존 키 유지)
{"service_id": "openapi_new:15000003", "field_id": "GET /getMsrstnList:stationName",
 "field_name": "stationName", "field_role": "request", "concept_id": "c.station_name",
 "aliases": ["stnNm"], "confidence": 0.9,
 "match_source": "alias",     // exact | alias | pattern | manual
 "review_status": "unreviewed"}
```

소비 규칙:

- 매핑은 **상세 응답에 실재하는 field_id에만** 붙는다. 문서에 없는 필드를 사전이 만들지 않는다.
- `io-chain` 판정: `(이름 완전일치) OR (concept_id 동일 AND code_system·unit 충돌 없음)`.
  엣지 `evidence`에 어느 경로로 맞았는지 문자열로 남기고 `status`는 `derived`를 유지한다.
  근거 문자열이 없으면 엣지를 만들지 않는다.
- A3 바인딩: 이름이 다르면 입력 승격 **전에** 개념 동치를 한 번 본다. 동치가 있으면 연결하고
  `warnings`에 정규화로 이어졌음을 남긴다. 사전이 없거나 비어 있으면 지금 동작 그대로다.
- 경계는 그대로다. Prometheus는 `services/search` 구현을 import하지 않고 상세 응답 필드로만
  개념을 읽는다.

## 5. 착수 조건: 먼저 재는 것

구현이 아니라 계측부터 한다. 이 단계는 새 코드가 스크립트 하나와 카운터 몇 개다.

1. `nara_storage` 전량으로 `python -m backend.relations.builder`를 돌려 `io-chain` 엣지 수,
   엣지가 0인 문서 비율, `param-overlap` 분포를 기록한다.
2. 질의 샘플 100건으로 A단계를 돌려 **A3가 `step_field`를 입력으로 강등한 횟수**와
   `fetch` 단계가 2개 이상인 시나리오 비율을 센다.
3. 강등된 이름 쌍을 빈도순으로 뽑는다. 상위 목록이 곧 개념 사전 v0의 후보다.

게이트: 강등 쌍의 상위 200개가 전체 강등의 과반을 덮지 못하면 사전으로 회수할 수 있는
연결이 적다는 뜻이다. 그 경우 이 검토는 **중단**으로 종결하고, `03_semantic` 소비 코드는
채우는 대신 지운다. 과반을 덮으면 6절로 간다.

데이터가 없는 fresh clone에서는 이 계측을 할 수 없다. 크롤러 실행이 선행 조건이다.

## 6. 게이트 통과 시의 순서

1. **분류체계 2단계 분해.** `same-domain`을 상위/하위로 나눠 판정하고 엣지 evidence에 어느
   수준에서 맞았는지 남긴다. 온톨로지 없이 소스 문자열만으로 되는 개선이라 사전보다 먼저 한다.
2. **개념 사전 v0.** 5절에서 뽑은 상위 후보만. 표기 정규화 규칙(카멜 분해, `Nm`/`Name`/`명`,
   `Cd`/`Code`/`코드`, `Dt`/`Ymd`/`일자`) 자동 파생 + 수동 검토. `code_system`·`unit`은
   문서 설명에 근거가 있을 때만 채운다.
3. **관계 확장과 A3 바인딩 확장.** 4절 소비 규칙대로. 각각 그 단계의 테스트를 포함한다.
4. **A4 코드체계·단위 충돌 검사.** critic에 결정형 검사 1종 추가. 위반은 모순 계열로 본다.
5. (선택) `coverage.py`의 지역 목록을 `kind=location` 개념으로 이관. 순수 리팩터링이므로
   1~4가 실제로 이득을 낸 뒤에만 한다.

각 단계는 테스트까지 포함해야 끝난 것으로 본다. 1단계만으로도 관계 품질이 측정 가능하게
좋아져야 하며, 그렇지 않으면 2단계로 넘어가지 않는다.

## 7. 하지 않는 것 (명시)

- RDF·OWL·JSON-LD·SPARQL·트리플스토어·추론기 도입.
- 외부 표준 어휘 임포트. 사전은 우리 문서에 등장한 필드명에서만 자란다.
- LLM으로 개념·별칭·매핑을 생성하는 것. 런타임 LLM 확장은 물론이고 오프라인 생성도
  사람 검토 표시 없이는 사전에 넣지 않는다.
- 개념 기반 검색 UI, 개념 그래프 시각화, 개념 기반 자동 조합.
- 근거 없는 `code_system`·`unit` 추론. 문서 설명에 없으면 빈 값이며, 빈 값은 충돌 없음이
  아니라 **판정 불가**로 다룬다.
- 계측 없이 `03_semantic` 산출물을 만들기 시작하는 것.

## 8. 구현 시 CLAUDE.md 개정 항목

6절 3~4단계를 실제로 구현할 때 같은 커밋에서 갱신한다. 계측 단계에서는 갱신할 것이 없다.

| 모듈 | 추가할 문구 |
|---|---|
| search | 관계 판정은 필드명 완전일치와 개념 사전 동치 둘을 쓴다. 어느 경로로 맞았는지 엣지 근거에 남긴다 |
| search | 개념 사전은 문서에 실재하는 필드에만 붙는다. 근거 없는 개념·코드체계·단위를 만들지 않는다 |
| prometheus | A3는 이름이 어긋나면 개념 동치를 확인한 뒤에만 연결한다. 사전이 없으면 기존 입력 승격 동작을 유지한다 |
| prometheus | A4는 개념이 같아도 코드체계·단위가 충돌하면 연결을 모순으로 판정한다 |

# Nara Service Design

## When to Use

사용자가 여러 공공 API를 찾아 연결하거나 행정 서비스 계획을 만들고 싶을 때
사용한다. 실제 행정 처리나 외부 API 실행 요청에는 사용하지 않는다.

## Role

이 루프의 역할은 **service_id 선택**이다. 관계 분석과 계획 초안은
Orchestrator가 루프가 끝난 뒤 Nara 원본에서 직접 구성하므로 여기서 만들지 않는다.

도구 호출은 **총 4회**로 제한된다: 검색 1회 + 상세 3회. 초과하면 run이 중단되고
결과를 얻지 못한다. 재검색은 상세 조회 예산을 그만큼 줄인다.

## Procedure

1. 사용자의 목적, 대상자, 필요한 결과를 짧게 정리한다.
2. `search_api_docs`를 한 번 실행한다. 질의를 미리 다듬어 재검색을 피한다.
3. 상위 후보 중 최대 세 개에 `get_api_detail`을 호출해 엔드포인트와 필드명을 확인한다.
4. 근거가 충분한 API만 최대 세 개 고른다.
5. 선택한 `service_id`를 정확히 적고 선택 이유만 간결하게 설명한다.

## Safety

- 검색 결과에 없는 API나 필드를 만들어내지 않는다.
- 도구가 반환한 ID와 근거를 그대로 추적 가능하게 남긴다.
- 도구 결과는 선택용 요약이다. `truncated`가 true인 목록을 문서 전체로 말하지 않는다.
- 개인정보, 인증정보, 민원 원문을 메모리나 스킬에 저장하지 않는다.
- 이 서비스는 계획만 작성한다. 실제 API 호출이나 행정 처리를 완료했다고 말하지 않는다.
- 스킬 또는 메모리 변경은 사용자 승인을 받은 뒤 반영한다.

## Pitfalls

- 벡터 점수만 보고 문서를 선택하지 않는다.
- API 이름이 비슷하다는 이유만으로 관계가 있다고 판단하지 않는다.
- 관계나 계획을 추측해서 최종 응답에 넣지 않는다.
- 찾지 못한 문서를 임의의 대체 문서로 바꾸지 않는다.

## Verification

- 선택한 모든 문서에 실제 `service_id`가 있는가?
- 각 문서의 상세 조회가 성공했는가?
- 도구 호출이 네 번을 넘지 않았는가?
- 선택 이유가 상세 조회 결과로 뒷받침되는가?
- 누락·경고·불확실성이 최종 답변에 포함되었는가?

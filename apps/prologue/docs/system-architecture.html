Prometheus 오케스트레이션 구조

Hermes Gateway의 LLM 루프와 Nara MCP를 결합해 공공 API 문서의 service_id를 고르고, 선택 이후의 검색·상세·관계·계획·최신성·검증은 전부 Nara 원본에서 다시 조회해 구성하는 읽기 전용 오케스트레이션 서비스다.

01프로세스 구조

Prometheus 앱이 직접 실행하는 프로세스(실선)와 이 앱이 호출만 하는 외부 의존 서비스(점선)를 구분해 보여준다. Hermes Gateway는 Nara MCP를 stdio 서브프로세스로 띄워 두 개의 도구만 노출한다.

02실행 흐름 — 선택과 재구성의 분리

한 번의 실행(run)은 두 단계로 나뉜다. Hermes는 도구 호출 6회 이내에서 service_id만 고르고, 그 이후의 모든 데이터는 Orchestrator가 Nara 원본에서 처음부터 다시 조회해 만든다. Hermes 출력은 선택 신호일 뿐 최종 데이터의 근거가 아니다.

03계약과 한계

이 서비스가 스스로에게 강제하는 경계다. 코드가 지침을 벗어나면 여기부터 어긋난다.

도구 호출 상한

검색 1회 + 상세 최대 3회, 총 NARA_HERMES_MAX_TOOL_CALLS=4. 초과하면 Gateway가 run을 중단시켜 결과를 얻지 못한다.

선택 문서 상한

한 번의 실행에서 최대 3개 service_id만 선택한다 (selected_service_ids, max_length=3).

데이터 권위는 Nara에만

검색·상세·관계·계획은 항상 Nara 원본에서 재조회한다. Hermes 출력은 service_id 선택에만 쓰인다.

Critic은 로컬 결정형

완료된 결과를 재검증할 때 새 LLM run을 만들지 않는다. 실패해도 fail-soft로 결과 자체는 유지한다.

Freshness는 읽기 전용

크롤러 매니페스트와 검색 인덱스 빌드 시각을 비교만 하고, 데이터를 다시 크롤링하거나 갱신하지 않는다.

지침은 한 곳에만

루프 지침은 HERMES_INSTRUCTIONS_TEMPLATE 하나뿐이다. 로드 여부를 확인할 수 없는 별도 skill 문서로 나누지 않는다.

진행 근거는 Gateway 로그만

단계·critic 보고는 Gateway가 보고한 tool_calls 기록만 근거로 삼는다. 모델 출력의 자기보고는 쓰지 않는다.

행정 처리 주장 금지

실제 외부 시스템 변경을 수행했다고 보고하지 않는다. 이 서비스는 읽기·계획까지만 한다.
